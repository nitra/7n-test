# Кап runtime-probe виходів + бюджет промпту для omlx-викликів

## Контекст і проблема

Аналіз `requests.jsonl` (myllm-проксі, вікно 07:42–08:02, 31 запит із cwd
`7n-test`) показав повільні (median 32.6s, p90 71.7s, max 171.8s) і
нестабільні виклики до локальної моделі `gemma-4-e4b-it-OptiQ-4bit`,
включно з серією `400 prefill_memory_exceeded`. Порівняння з іншими
клієнтами проксі (median 8.2s) — мотиваційне, не доказове: воркло-ад
різний. Доказовим є розтин самих payload'ів (нижче).

Важлива умова середовища: локальна модель обслуговує **один промпт
одночасно** (одно-слотова черга oMLX). Тобто memory-guard відмова — це
не конкуренція паралельних запитів, а залишкова (ще не вивільнена)
пам'ять від попереднього запиту; вона розсмоктується сама за десятки
секунд (у логах: після трьох 400 поспіль той самий за розміром промпт
пройшов через ~33 с без жодних змін).

### Проблема 0 (головна, знайдена розтином payload): необмежений runtime-probe вихід

Розтин найбільшого payload (124 577 символів, 07:52:43) показав:
retry-накопичення відсутнє (жодного маркера «## Спроба»), код-фенси
~1k, а **~122k з 124k — один рядок runtime-probe**:

```
Реальні виходи `readSurvived` (runtime-probe — використовуй для expected, не вгадуй):
- readSurvived("") → [{"file":"npm/src/assess-need.mjs","mutants":[...весь COVERAGE.md...
```

Механізм:

- `npm/src/lib/runtime-probe.mjs:112` — `output: JSON.stringify(out)`
  **без жодного ліміту розміру**;
- `npm/src/gen-tests.mjs:391-401` (`buildProbeLines`) вставляє кожен
  probe-рядок у block-промпт verbatim (`gen-tests.mjs:518`);
- probe викликає exports з edge-інпутами (`null`, `""`, …), і
  `readSurvived("")` виконав `readFile(join("", 'COVERAGE.md'))` —
  **прочитав реальний COVERAGE.md проєкту з робочого cwd** і весь
  mutation-звіт (з вбудованими сніпетами коду) поїхав у промпт;
- block-промпт будується per export/block, тож той самий дамп
  повторювався в кожному виклику для цього файлу — серія 124–177k
  запитів упродовж 10 хвилин (07:52–08:02).

Тобто probe на функціях з I/O дає environment-залежні гігантські й
недетерміновані «expected» значення — це і причина розміру, і окрема
загроза якості тестів.

### Проблема 1: `max_completion_tokens` завжди 32768

Значення береться зі статичного `~/.pi/agent/models.json`
(`maxTokens: 32768`) через vendored `@earendil-works/pi-ai`
(`openai-completions.js:437-444`); `callText`/`callAgent`
(`npm/src/lib/pi-client.mjs:84,127`) не мають per-call override. Це
гігієнічна проблема (захист від runaway-генерації відсутній
диференційовано), але **не** доведена причина 400-ок: спостережений
guard — prefill (розмір промпту), і чи резервує oMLX пам'ять під
`max_completion_tokens` — не встановлено.

### Проблема 2: `fix-tests.mjs` конкатенує всі падаючі файли без ліміту

`buildFixTestsPrompt` (`npm/src/fix-tests.mjs:118`) складає в один
промпт ПОВНІ секції всіх падаючих файлів (тест `.slice(0,6000)` +
source `.slice(0,4000)` + весь vitest-вивід) — розмір лінійно росте від
кількості одночасних падінь. У розібраних логах цей шлях не був
джерелом великих payload'ів (усі 11 великих — block-промпти gen-tests),
але клас проблеми той самий: жодного сумарного бюджету.

### Проблема 3: retry-цикли не читають структуровану помилку сервера

oMLX повертає 400 з тілом
`{"error":{"code":"prefill_memory_exceeded","estimated_bytes":…,"limit_bytes":…}}`,
але обидва retry-шари матчать лише `error.message` за regex
(`MEMORY_ERROR_RE`, `pi-client.mjs:32`). `estimated_bytes`/`limit_bytes`
— це байти **GPU/Metal-пам'яті** (дельта ~300 MB), їх НЕ МОЖНА
використовувати як «скільки символів промпту зрізати» — лише для
діагностики/логів.

### Проблема 4 (виправлена у WIP): ідентичний миттєвий retry

Стара гілка `reset` у `resolveLoopCallFailure` (`gen-tests.mjs`) на
memory-guard без згенерованого блоку повторно слала байт-в-байт той
самий `basePrompt` без затримки — 3 запити з ідентичним хешем за <2 с у
логах. Working tree вже містить незакомічений fail-fast фікс (див.
«Пов'язані зміни»).

## Мета

1. Обмежити розмір runtime-probe виходів (усуває ~95% спостереженого
   розміру промптів).
2. Дати memory-guard відмовам обмежений backoff-retry (одно-слотова
   черга: пам'ять вивільняється сама), замість миттєвого повтору чи
   миттєвої смерті.
3. Другим ешелоном (фаза 2) — спільний бюджет промпту й per-call
   `maxTokens`, щоб клас проблеми «безлімітна секція» не повторився в
   іншому місці.

## Non-goals

- Не чіпаємо `coverage-fix.mjs`/`coverage-fix-extract.mjs` (свідомо
  вузькі за дизайном).
- Не змінюємо вибір моделі і не додаємо провайдерів.
- Не редагуємо vendored SDK у node_modules.
- Перф-цілі в acceptance criteria не ставимо — латентність вважаємо
  наслідком розміру промптів, вимірюємо розмір.

## Пов'язані зміни

Fail-fast фікс проблеми 4 (memory-guard → throw наверх, без тихого
повтору) закомічений як `6f63570 fix(pi-client): omlx memory-guard
rejection terminates instead of retrying`. Ця спека **модифікує** його
поведінку в §Д2: замість «одразу термінально» — обмежений
backoff-retry у `withRetry`, і лише після вичерпання — поточний
термінальний шлях (друк тіла запиту + throw). Друк 124k-тіла в stdout
має відбуватись тільки на фінальному провалі, не на кожній спробі.

## Зв'язок зі спекою myllm `docs/spec-llm-efficiency.md`

Ця спека — **клієнтська половина спільного вектора** з програмою
економії LLM-викликів у репо myllm (`docs/spec-llm-efficiency.md`,
напрями A–E: response-кеш проксі, калібрування critic/refine,
дедуплікація docgen, швидкість декодування oMLX, метрики UI). Там ця
спека зареєстрована як **напрям F**. Точки стикування:

- **Guard-відмови**: efficiency-спека рахує 107 prefill-відмов і
  приписувала лікування `compress.rs` (проксі). Розтин показав: для
  2-message one-shot запитів gen-tests компресія проксі структурно
  безсила (обидва повідомлення protected), корінь — probe-дамп на
  клієнті. Д1 тут — первинне лікування; `compress.rs` лишається для
  multi-message агент-сесій (`mcp-omlx.mjs`).
- **Префікс-кеш oMLX**: детермінований probe-вихід (tmp-cwd, Д1)
  робить повторні промпти байт-стабільними → вищий hit-rate і для
  префікс-кешу сервера, і для майбутнього response-кешу проксі
  (напрям A), який рахує exact-match ключ.
- **Response-кеш і retry**: кеш проксі зберігає лише 200-відповіді,
  тож backoff-retry Д2 (повтор ідентичного промпту після 400) з кешем
  не конфліктує.
- **Ключ кешу і per-call maxTokens (Д5)**: ключ напряму A вже включає
  `max_tokens` — варіативний `max_completion_tokens` по taskKind
  сегментує кеш коректно, але про це треба пам'ятати при звірці
  hit-rate (однаковий промпт із різним maxTokens = різні ключі).

## Дизайн

### Д1. Кап runtime-probe виходів (основний фікс)

У `npm/src/lib/runtime-probe.mjs`, у точці серіалізації результату
(`:112` та аналогічні місця для constant/`helperProbe`/fetch- і
time-probe):

- Новий ліміт `PROBE_OUTPUT_MAX_CHARS` (стартово **600**; конфіг не
  потрібен — константа з тестом).
- Якщо `JSON.stringify(out).length > PROBE_OUTPUT_MAX_CHARS` — замість
  значення повертається **shape-summary**: стислий опис форми, напр.
  `Array(34) of {file: string, mutants: Array(12) of {line, col, mutantType, original, replacement}}`
  або `Object{keys: [...]}, ~123456 chars` для об'єктів. Модель знає
  структуру для asserts на форму, але не отримує і не копіює гігантський
  дамп як expected-значення.
- Shape-summary будується рекурсивно з обмеженою глибиною (2-3 рівні) і
  сама теж капається (`PROBE_OUTPUT_MAX_CHARS`).
- Додатковий ліміт на всю probe-секцію одного export (напр., 12 рядків)
  — щоб багато середніх виходів теж не роздували промпт.

Доповнення (та сама причина, інший вектор): **запускати probe-сабпроцес
із cwd у порожній тимчасовій директорії**, а не в корені проєкту — тоді
відносні I/O-читання (`readSurvived("")` → `COVERAGE.md`) повертають
порожньо/помилку замість реального файлу, і expected-значення
детерміновані між машинами. Це окремий крок, сумісний із капом
(кап — запобіжник, tmp-cwd — усунення джерела).

### Д2. Memory-guard: обмежений backoff-retry у `pi-client.mjs`

`withRetry` (`pi-client.mjs:61`):

- Розбирати структуроване тіло помилки, коли доступне: додати на об'єкт
  помилки `error.omlxCode`, `error.estimatedBytes`, `error.limitBytes`
  (діагностика/лог, НЕ керування розміром промпту — див. Проблему 3).
  `MEMORY_ERROR_RE` лишається fallback-детектором за message.
- Memory-guard клас (по `omlxCode === 'prefill_memory_exceeded'` або
  regex-fallback) стає **retryable з окремим, довшим графіком**:
  до 3 спроб із затримками ~15s / 30s / 60s + jitter (одно-слотова
  черга; у логах пам'ять вивільнилась за ~33 с). Звичайні
  connection-помилки зберігають поточний графік
  (`BASE_DELAY_MS`/`MAX_DELAY_MS`).
- Після вичерпання — `failOnMemoryGuard`: друк тіла запиту + throw, і
  **обов'язково зберегти структуровані поля** на прокинутій помилці
  (`cause` або копіювання полів) — WIP-версія створює новий `Error` з
  самим message і губить їх.
- Нові env-кноби за аналогією з наявними:
  `N_PI_MEMORY_RETRY_ATTEMPTS` (default 3),
  `N_PI_MEMORY_RETRY_DELAY_MS` (default 15000).

Виклики в `gen-tests.mjs`/`fix-tests.mjs`, що зараз пробивають
memory-guard наверх (WIP-diff), лишаються як є: якщо `pi-client`
вичерпав memory-retry — прогін завершується. Shrink-on-retry НЕ
робимо (проти залишкової пам'яті одно-слотової черги він не допомагає,
а бюджет фази 2 обмежує промпт апріорі).

### Д3 (фаза 2). `npm/src/lib/prompt-budget.mjs` — defense-in-depth

Спільний модуль, щоб клас «безлімітна секція» не повторився. Два
роздільні API (не змішувати внутрішньопромптове обрізання з батчингом):

```js
/** @param {'header'|'block'|'fix'|'single-file'} taskKind */
export function budgetFor(taskKind) // → { maxPromptChars, maxTokens }

/**
 * Внутрішньопромптове обрізання: ріже/дропає низькопріоритетні chunks,
 * поки сумарно не влізе. Останній user-запит (сама задача) — захищений.
 * @param {Array<{text: string, priority: number}>} chunks
 * @returns {{ text: string, dropped: string[] }}
 */
export function fitToBudget(chunks, maxChars)

/**
 * Батчинг цілих одиниць (файлів) під бюджет: повертає підмножину і чергу.
 * @param {Array<{key: string, size: number}>} items
 * @returns {{ included: string[], deferred: string[] }}
 */
export function packBatch(items, maxChars)
```

Стартові бюджети (уточнюються на review; калібрувати після Д1, коли
стане видно реальний профіль розмірів):

| taskKind | maxPromptChars | maxTokens |
|---|---|---|
| `header` | 8 000 | 2 048 |
| `block` | 40 000 | 8 192 |
| `single-file` | 60 000 | 16 384 |
| `fix` | 60 000 | 16 384 |

### Д4 (фаза 2). `fix-tests.mjs`: батчинг через `packBatch`

`buildFixTestsPrompt` → повертає
`{ prompt, included, deferred }`; цикл `fixFailingTests`
(`fix-tests.mjs:271-295`):

- `deferred` файли йдуть **першими** в наступному проході — жоден файл
  не може бути відкладеним двічі поспіль (анти-starvation).
- Файл, що сам-один перевищує бюджет, отримує **соло-виклик** із
  жорсткішим внутрішнім обрізанням через `fitToBudget` (ріжемо
  vitest-вивід і source-секцію, тест-код захищений) — ніколи не
  скипається мовчки.
- Семантика `MAX_FIX_ATTEMPTS`: лічильник **проходів** лишити, але
  прохід, який лише розвантажив deferred-чергу (не ретраїв уже
  спробувані файли), не рахувати як спробу для файлів із черги —
  практично: attempts рахуються per-file (скільки разів файл був
  included), а не per-loop.

### Д5 (фаза 2). Per-call `maxTokens` + захист від обрізаної генерації

- `callText`/`callAgent` отримують `opts.maxTokens`. **Перший крок
  імплементації фази 2 — спайк**: чи приймає SDK per-call `maxTokens`
  (через session options або підміну `modelDef.maxTokens` на
  резольваному model-об'єкті). Якщо ні — ескалація в окремий тикет на
  зміну `~/.pi/agent/models.json` (зачіпає інші проєкти, рішення поза
  цим repo).
- Обов'язково разом із зниженням `maxTokens`: `callText` пробрасывает
  `stopReason` останнього повідомлення; на `stopReason === 'length'`
  (обрізана генерація) — один повтор із подвоєним `maxTokens` (до стелі
  моделі), інакше цикл у `generateBlockWithLoop` палитиме спроби на
  «invalid block», не знаючи причини.
- `gen-tests.mjs`/`fix-tests.mjs` передають `budgetFor(kind).maxTokens`.

## Альтернативи розглянуті

- **Обрізання probe-виходу до перших N символів з маркером** —
  відхилено: модель копіює обрізаний JSON у expected, тест гарантовано
  падає. Shape-summary дає структуру без сміття.
- **Дроп probe-рядка з приміткою** — відхилено: втрачається інформація
  про форму результату, яка і є цінністю probe.
- **Shrink-промпту при memory-guard retry** — відхилено: одно-слотова
  черга означає, що відмова — залишкова пам'ять попереднього запиту;
  очікування лікує, стискання — ні (підтверджено логами: той самий
  промпт пройшов через ~33 с). Бюджет фази 2 обмежує розмір апріорі.
- **Тільки знизити глобальний `maxTokens` у `~/.pi/agent/models.json`** —
  відхилено як єдине рішення: не чіпає проблему 0 і 2; лишається
  умовним fallback у Д5.
- **Точкові константи замість спільного `prompt-budget`** — відхилено
  для фази 2: без спільної точки правди наступний колер повторить клас
  помилки (що ця ж спека і продемонструвала: агент-аналіз спершу
  хибно атрибутував джерело розміру).

## Ризики та граничні випадки

- **Shape-summary погіршує probe-цінність для «середніх» виходів**
  (легітимний вихід на 700 символів теж became summary) — поріг 600
  емпіричний; переглянути після першого прогону, критерій: скільки
  згенерованих тестів використовують probe-значення в expect().
- **tmp-cwd для probe може зламати probes, які легітимно читають
  fixture поруч із модулем** — перевірити на поточному наборі файлів;
  якщо є такі — залишити cwd, покладатись лише на кап.
- **SDK може не підтримувати per-call `maxTokens`** (Д5) — спайк
  першим кроком фази 2; fallback — глобальний конфіг (ескалація,
  high side-effect на інші проєкти).
- **Backoff 15-60 с на memory-guard подовжує невдалі прогони** —
  прийнятно: альтернатива (миттєвий fail) вбиває багатогодинний
  batch-прогін через тимчасовий стан сервера.

## Acceptance criteria

Фаза 1:

1. Unit-тести `runtime-probe`: вихід > `PROBE_OUTPUT_MAX_CHARS` →
   shape-summary (масив, об'єкт, вкладені структури, довгий рядок);
   вихід ≤ капу — незмінний; probe-секція одного export ≤ ліміту рядків.
2. Інтеграційний тест на `buildProbeLines`/`buildBlockPrompt`: export,
   що повертає >100k об'єкт, дає block-промпт < 40 000 символів.
3. Probe-сабпроцес із tmp-cwd: `readSurvived("")`-подібний виклик
   (відносний `readFile`) повертає порожній результат, а не вміст
   реального файлу проєкту.
4. Unit-тести `pi-client`: (a) 400-тіло з `omlx_code` →
   `error.omlxCode/estimatedBytes/limitBytes` присутні, включно з

## Результат верифікації (2026-07-04, e2e sandbox-прогін)

Фази 1 і 2 реалізовані (ADR 0001, ADR 0002; релізи `@7n/test@0.11.2`
і `0.12.0`) і перевірені e2e-прогоном повного пайплайна на
sandbox-проєкті через локальну модель (78 LLM-викликів у лозі
myllm-проксі):

- `max_completion_tokens` варіюється за taskKind: 2048/8192/16384
  (було незмінно 32768) — критерій 7 фази 2 виконано.
- Максимальний промпт 54.7k символів (у fix-бюджеті 60k; block <10k)
  проти 124–177k до фіксів.
- 0 відмов `prefill_memory_exceeded` (у інциденті — 3 за 2 секунди).
- Канарковий export із відносним `readFileSync` не затягнув файлів
  проєкту — tmp-cwd probe працює (критерій 3 фази 1).
- Цикл fix-tests зупинився після 3 per-file спроб без зациклення.

**Відомий залишок:** `callAgent` (agent-mode, pi-native fix-engine та
capture-хуки) шле запити без `maxTokens`; контекст агентних сесій
росте з tool-calls (спостережено до ~54k). Якщо цей шлях почне
впиратись у memory guard — рішення те саме: streamFn-обгортка
(`applyMaxTokens`) для `callAgent` + SDK-компакція. Свідомо поза
обсягом цієї спеки.
